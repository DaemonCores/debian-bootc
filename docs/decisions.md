# Decisions

Intentional choices visible in the code that can look unusual to a newcomer. These are deliberate, not defects. For problems, see [inconsistencies-tech-debt](inconsistencies-tech-debt.md). For narrative trade-off discussion, see [justifications](justifications.md).

| Decision | Why chosen | What NOT to do | Source |
|----------|------------|----------------|--------|
| Base image `debian:trixie` is left unpinned (no digest) | Rebuilds pick up Debian security updates automatically, without a manual digest bump | Don't pin `FROM debian:trixie` to a `@sha256:` digest. The residual risk is tracked in [TD-20261018-unpinned-base-images](tech-debt/TD-20261018-unpinned-base-images.md) | [src: file: Containerfile:3] |
| Both images install the single project kernel (per architecture and page size, see the two arm64 kernels below) through the virtual name `linux-image-${KERNEL_VARIANT}-${ARCH}` (default `minimal`); the standard image adds the same per-arch `linux-modules-*` packages as the minimal one, and Debian's `linux-image-amd64` / `linux-image-arm64` is no longer installed (reverses the earlier standard-image-keeps-Debian-kernel decision) | One kernel to build, patch and support; the drivers Debian's kernel carried ship as modules, so hardware support is not reduced. A second `/usr/lib/modules/<kver>/` would also fail bootc lint. The custom kernel is the deb `daemoncores-kernel-<kver>`: it Provides `linux-image-minimal-<arch>` and Conflicts with and Replaces the Debian `linux-image-<kver>` it overlaps, like the ostree package does with libostree | Don't make the custom kernel Provide `linux-image-<arch>`, don't install Debian's `linux-image-<arch>` next to it, and don't install `linux-headers` (not published in the project APT repo) | [src: file: Containerfile:18] [src: file: Containerfile:88-93] [src: file: workflows/bootc-debs-builder/packages.yml:171-183] |
| `.github/workflows/pipeline.yml` is a thin caller of the shared `DaemonCores-CI` `full-pipeline.yml` | GitHub evaluates triggers and concurrency in the caller, not in the reusable workflow; the whole job graph lives in the shared reusable workflow | Don't add jobs or steps to `pipeline.yml`. Don't move triggers or concurrency into the shared workflow | [src: file: .github/workflows/pipeline.yml:3-15] |
| Per-deb content cache keyed only on declared `sources` paths and non-secret `env`; `secret-env` is never hashed | An unchanged package is restored from the published APT repo instead of rebuilt | Don't add a build input (file, version, env var) without declaring it under that package's `sources`/`env`, or the cache serves a stale `.deb`. Don't put secrets in `env` | [src: file: workflows/bootc-debs-builder/packages.yml:7-10] |
| Every runtime test must declare a `diag` command; the harness fails the build otherwise | A failing boot test must always capture the runtime state behind the failure | Don't add a test to `workflows/tests.yml` without `diag`. Don't drop the `arch`/`variant` gates on target-specific tests | [src: file: workflows/tests.yml:9-12] |
| APT signing key fetched with `wget` and checked against `BOOTC_GPG_SHA256`, a build argument the CI derives from the `APT_GPG_KEY` secret (the published key must carry the secret's fingerprint) | The build fails if the downloaded key bytes differ from the digest; no hash is committed, so rotation needs no commit | Don't replace this with `ADD <url>` or skip `sha256sum -c`. The Containerfile default only serves local builds | [src: file: Containerfile:38-41] [src: file: Containerfile:74-78] |
| `policy-rc.d` returns `101` during the build and is deleted in the final phase | The build container has no init; services must start only on the real first boot | Don't remove the hook early or start daemons in a `RUN`. Don't ship it in the final image | [src: file: src/debianpreinstall/usr/sbin/policy-rc.d:3-8] [src: file: Containerfile.minimal:202] |
| Kernel finalization (relocation into `/usr/lib/modules/<kver>/`, dracut initramfs) runs from a `postinst.d` hook shipped in the `bootc` deb | Any Debian-based downstream image that installs or updates a kernel gets the OSTree layout automatically | Don't require downstream Containerfiles to call `bootc-finalize` by hand, and don't move the hook out of the `bootc` package | [src: file: workflows/bootc-debs-builder/bootcpostinstall/etc/kernel/postinst.d/zz-bootc-finalize:3-9] |
| APT signing key rotated by a CI cron that writes the `APT_GPG_KEY` secret; nobody pushes packages by hand | The APT repo is a GitHub Pages site, so only GitHub can publish to it, and an immutable bootc OS has no reason to push a package after the image build | Don't print, export as an output or upload the private key; don't pin a hash by hand: the pipeline derives it | [src: user:pikatsuto:2026-10-18: KT-5 decision]; `DaemonCores-CI/.github/workflows/rotate-apt-key.yml` (reusable, called by `.github/workflows/rotate-apt-key.yml`) |
| GRUB is always built from the Fedora source (`rhboot/grub2`), never taken from Debian | bootc and bootupd need the GRUB modules and configuration of the Fedora build; Debian's GRUB has neither | Don't stage or install Debian's `grub-efi-*-signed`, not even as an arm64 fallback | [src: user:pikatsuto:2026-10-19: GRUB Fedora is mandatory] [src: file: workflows/bootc-debs-builder/packages.yml:799] |
| The Fedora GRUB follows the head of the `rhboot/grub2` default branch (rolling), resolved by `upstream-track` before each build; the package version is derived from the source (`1+<GRUB>+<commit date>+<branch>`) | Same rolling-release policy as the rest of the stack: no commit pinned in the repository, and a head that fails to build keeps the last-good deb | Don't reintroduce `GRUB_PINNED_COMMIT`, `GRUB_FEDORA_BRANCH` or a hard-coded `GRUB_VER` | [src: user:pikatsuto:2026-10-19: pin the Fedora mainline branch, not a commit] [src: file: workflows/bootc-debs-builder/packages.yml:786-789] |
| arm64 has two boot profiles chosen by `LABEL org.daemoncores.boot-profile`: `generic` (Fedora GRUB, UEFI machines and VMs) and `embedded` (U-Boot, boards); amd64 is always generic | A UEFI arm64 machine needs GRUB like amd64, while Raspberry Pi class devices load U-Boot and have no use for GRUB | Don't derive the boot stack from the architecture alone, and don't ship Debian's GRUB for the generic profile | [src: file: Containerfile.minimal:93] |
| The minimal kernel saves RAM by removing kernel features (BTF, ftrace, profiling, scheduler debug, kexec/crash dump, embedded config, oversized `NR_CPUS`), never hardware support | The image cannot know its hardware, and a module costs nothing until its device appears; the debugging and capture machinery is resident on every boot | Don't disable a driver or subsystem to reach a memory figure; add the missing driver instead | [src: file: workflows/bootc-debs-builder/kernel/config:331-359] |
| Upstream sources are rolling: no version or commit is pinned in the repository, `upstream-track` resolves the latest release (or the branch head) before each build, and a build that cannot resolve or compile keeps the last-good published deb | A pin is a manual chore that lets the image rot, and a pin specific to one package or repository cannot be shared | Don't commit a version, commit or checksum for a tracked source; track it with `track:` in `packages.yml` | [src: file: workflows/bootc-debs-builder/packages.yml:1] |
| Shared pipelines, scripts and tests live in `DaemonCores-CI`; this repository only holds callers and its own sources, and its `Makefile` fetches the CI repository into an untracked `.ci` on demand | Several repositories need the same checks, and a copy per repository drifts | Don't add a repository-specific workflow, rotation script or shared test here | [src: file: Makefile:130] |
| Hardware support is never reduced to pass a test or save space: the DRM drivers stay (built as modules) in every kernel, and a boot failure is diagnosed, not worked around by removing a driver | The image cannot know its hardware, and the live installer needs KMS | Don't disable `CONFIG_DRM` or any driver subsystem; fix the cause of the failure | [src: file: workflows/bootc-debs-builder/kernel/config:201-203] |
| The kernel is the kernel.org tarball of the newest stable or longterm release whose series every patch source already provides (CachyOS, ROCKNIX), resolved before each build by the `track:` entry (`kernel-org: stable`, `require-patches: kernel/patches.yml`); a release the patches have not caught up with is skipped, not built and failed with its sha256 from `sha256sums.asc`; the deb version is pinned to `<kernel>-1` so the module entries fetch the same tarball | A single home-built kernel replaces Debian's kernel source; the rolling release keeps the last-good deb when a new kernel does not build, and the checksum is verified before extraction | Don't use `apt-get source linux`, don't commit a kernel version or checksum, don't build modules against a different tarball than the image | [src: file: workflows/bootc-debs-builder/lib/kernel-source.sh:1-45] [src: file: workflows/bootc-debs-builder/packages.yml:90-100] |
| Kernel patches are never committed: `kernel/patches.yml` lists official upstream URLs (`{series}` / `{version}` placeholders), each with a stage, a license and a class (`kernel` or `module`); `kernel_apply_patches` downloads them, checks the sha256 against `patches.lock.json`, dry-runs, then applies in manifest order, and any failure stops the build | The tree stays reproducible from upstream sources, a silently changed upstream patch is caught by the guard, and a patch that no longer applies to the rolling kernel breaks loudly instead of being skipped. A patch that can be a module (tristate driver or header) is class `module` and only applied for the module build; otherwise it is class `kernel`. Mixing both classes is allowed, conflicts are not | Don't commit `.patch` files, don't skip or silently drop a patch that fails to apply, don't pin a kernel commit, and don't refresh `patches.lock.json` without reviewing the diff | [src: file: workflows/bootc-debs-builder/kernel/patches.yml:28] [src: file: workflows/bootc-debs-builder/lib/kernel-patches.sh:43] |
| Android phones are out of scope for the embedded profile; it covers arm64 boards whose firmware loads U-Boot | Phones need their own boot chain and vendor trees and live in a separate repository | Don't add phone SoC patches or device trees to `kernel/patches.yml` or the `kernel/modules/*` overlays | [src: file: Containerfile.minimal:12] |
| The minimal image keeps systemd and dbus (option A) rather than a lighter init | The login stack, `bootc`, `systemd-timesyncd` and ssh depend on them; the memory savings come from kernel machinery, not from replacing the init | Don't swap the init or drop dbus to chase the idle-RAM target without a new decision | [src: file: docs/minimal.md:103] [src: file: Containerfile.minimal:190] |
| Inference-oriented kernel options (lazy preemption, madvise-only THP, multi-gen LRU, zram, zswap off by default) are added without measurement | Only compatibility was checked | Don't claim a performance gain without a measurement |
| arm64 has two kernels, 4 KB pages (Raspberry Pi 3 and 4) and 16 KB pages (Raspberry Pi 5, RK3588), published as two images (`<tag>` and `<tag>-16k`); it is the one exception to the single-kernel rule, amd64 keeps one kernel | The page size is a compile-time choice, so it cannot be a module, and the Cortex-A53 has no 16 KB granule (Cortex-A53 TRM). The owner keeps the old devices working without giving up the gains of recent hardware, and 16 KB pages are becoming the norm | Don't put `ARM64_16K_PAGES` in the shared `kernel/config` (it would stop the Pi 3 and Pi 4 from booting), don't install one kernel's modules on the other, and don't add a third page size without the same reasoning | [src: file: workflows/bootc-debs-builder/kernel/config:365] [src: file: docs/kernel-patches.md:1] |
