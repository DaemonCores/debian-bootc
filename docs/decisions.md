# Decisions

Intentional choices visible in the code that can look unusual to a newcomer. These are deliberate, not defects. For problems, see [inconsistencies-tech-debt](inconsistencies-tech-debt.md). For narrative trade-off discussion, see [justifications](justifications.md).

| Decision | Why chosen | What NOT to do | Source |
|----------|------------|----------------|--------|
| Base image `debian:trixie` is left unpinned (no digest) | Rebuilds pick up Debian security updates automatically, without a manual digest bump | Don't pin `FROM debian:trixie` to a `@sha256:` digest. The residual risk is tracked in [TD-20261018-unpinned-base-images](tech-debt/TD-20261018-unpinned-base-images.md) | [src: file: Containerfile.base:8] |
| Both images install the single project kernel (per architecture and page size, see the two arm64 kernels below) through the virtual name `linux-image-${KERNEL_VARIANT}-${ARCH}` (default `minimal`); the standard image adds the same per-arch `linux-modules-*` packages as the minimal one, and Debian's `linux-image-amd64` / `linux-image-arm64` is no longer installed (reverses the earlier standard-image-keeps-Debian-kernel decision) | One kernel to build, patch and support; the drivers Debian's kernel carried ship as modules, so hardware support is not reduced. A second `/usr/lib/modules/<kver>/` would also fail bootc lint. The custom kernel is the deb `daemoncores-kernel-<kver>`: it Provides `linux-image-minimal-<arch>` and Conflicts with and Replaces the Debian `linux-image-<kver>` it overlaps, like the ostree package does with libostree | Don't make the custom kernel Provide `linux-image-<arch>`, don't install Debian's `linux-image-<arch>` next to it, and don't install `linux-headers` (not published in the project APT repo) | [src: file: Containerfile:15] [src: file: Containerfile.base:60-65] [src: file: workflows/bootc-debs-builder/packages.yml:196-208] |
| `.github/workflows/pipeline.yml` is a thin caller of the shared `DaemonCores-CI` `full-pipeline.yml` | GitHub evaluates triggers and concurrency in the caller, not in the reusable workflow; the whole job graph lives in the shared reusable workflow | Don't add jobs or steps to `pipeline.yml`. Don't move triggers or concurrency into the shared workflow | [src: file: .github/workflows/pipeline.yml:3-15] |
| Per-deb content cache keyed only on declared `sources` paths and non-secret `env`; `secret-env` is never hashed | An unchanged package is restored from the published APT repo instead of rebuilt | Don't add a build input (file, version, env var) without declaring it under that package's `sources`/`env`, or the cache serves a stale `.deb`. Don't put secrets in `env` | [src: file: workflows/bootc-debs-builder/packages.yml:7-10] |
| Every runtime test must declare a `diag` command; the harness fails the build otherwise | A failing boot test must always capture the runtime state behind the failure | Don't add a test to `workflows/tests.yml` without `diag`. Don't drop the `arch`/`variant` gates on target-specific tests | [src: file: workflows/tests.yml:9-12] |
| APT signing key fetched with `wget` and checked against `BOOTC_GPG_SHA256`, a build argument the CI derives from the `APT_GPG_KEY` secret (the published key must carry the secret's fingerprint) | The build fails if the downloaded key bytes differ from the digest; no hash is committed, so rotation needs no commit | Don't replace this with `ADD <url>` or skip `sha256sum -c`. The `Containerfile.base` default only serves local builds | [src: file: Containerfile.base:49-54] [src: file: Containerfile.base:61-66] |
| `policy-rc.d` returns `101` during the build and is deleted in the final phase | The build container has no init; services must start only on the real first boot | Don't remove the hook early or start daemons in a `RUN`. Don't ship it in the final image | [src: file: src/debianpreinstall/usr/sbin/policy-rc.d:3-8] [src: file: Containerfile.minimal:154] |
| Kernel finalization (relocation into `/usr/lib/modules/<kver>/`, dracut initramfs) runs from a `postinst.d` hook shipped in the `bootc` deb | Any Debian-based downstream image that installs or updates a kernel gets the OSTree layout automatically | Don't require downstream Containerfiles to call `bootc-finalize` by hand, and don't move the hook out of the `bootc` package | [src: file: workflows/bootc-debs-builder/bootcpostinstall/etc/kernel/postinst.d/zz-bootc-finalize:3-9] |
| APT signing key rotated by a CI cron that writes the `APT_GPG_KEY` secret; nobody pushes packages by hand | The APT repo is a GitHub Pages site, so only GitHub can publish to it, and an immutable bootc OS has no reason to push a package after the image build | Don't print, export as an output or upload the private key; don't pin a hash by hand: the pipeline derives it | [src: user:pikatsuto:2026-10-18: KT-5 decision]; `DaemonCores-CI/.github/workflows/rotate-apt-key.yml` (reusable, called by `.github/workflows/rotate-apt-key.yml`) |
| GRUB is always built from the Fedora source (`rhboot/grub2`), never taken from Debian | bootc and bootupd need the GRUB modules and configuration of the Fedora build; Debian's GRUB has neither | Don't stage or install Debian's `grub-efi-*-signed`, not even as an arm64 fallback | [src: user:pikatsuto:2026-10-19: GRUB Fedora is mandatory] [src: file: workflows/bootc-debs-builder/packages.yml:611] |
| The Fedora GRUB follows the head of the `rhboot/grub2` default branch (rolling), resolved by `upstream-track` before each build; the package version is derived from the source (`1+<GRUB>+<commit date>+<branch>`) | Same rolling-release policy as the rest of the stack: no commit pinned in the repository, and a head that fails to build keeps the last-good deb | Don't reintroduce `GRUB_PINNED_COMMIT`, `GRUB_FEDORA_BRANCH` or a hard-coded `GRUB_VER` | [src: user:pikatsuto:2026-10-19: pin the Fedora mainline branch, not a commit] [src: file: workflows/bootc-debs-builder/packages.yml:589-592] |
| arm64 has two boot profiles chosen by `LABEL org.daemoncores.boot-profile`: `generic` (Fedora GRUB, UEFI machines and VMs) and `embedded` (U-Boot, boards); amd64 is always generic; `bootupd`, which depends on GRUB, is installed in the `generic` profile only | A UEFI arm64 machine needs GRUB like amd64, while Raspberry Pi class devices load U-Boot and have no use for GRUB | Don't derive the boot stack from the architecture alone, and don't ship Debian's GRUB for the generic profile | [src: file: Containerfile.minimal:101] [src: file: Containerfile.minimal:120-122] |
| The minimal kernel saves RAM by removing kernel features (BTF, ftrace, profiling, scheduler debug, kexec/crash dump, embedded config, oversized `NR_CPUS`), never hardware support | The image cannot know its hardware, and a module costs nothing until its device appears; the debugging and capture machinery is resident on every boot | Don't disable a driver or subsystem to reach a memory figure; add the missing driver instead | [src: file: workflows/bootc-debs-builder/kernel/config:333-361] |
| Upstream sources are rolling: no version or commit is pinned in the repository, `upstream-track` resolves the latest release (or the branch head) before each build, and a build that cannot resolve or compile keeps the last-good published deb | A pin is a manual chore that lets the image rot, and a pin specific to one package or repository cannot be shared | Don't commit a version, commit or checksum for a tracked source; track it with `track:` in `packages.yml` | [src: file: workflows/bootc-debs-builder/packages.yml:78] |
| Shared pipelines, scripts and tests live in `DaemonCores-CI`; this repository only holds callers and its own sources, and its `Makefile` fetches the CI repository into an untracked `.ci` on demand | Several repositories need the same checks, and a copy per repository drifts | Don't add a repository-specific workflow, rotation script or shared test here | [src: file: Makefile:130] |
| Hardware support is never reduced to pass a test or save space: the DRM drivers stay (built as modules) in every kernel, and a boot failure is diagnosed, not worked around by removing a driver | The image cannot know its hardware, and the live installer needs KMS | Don't disable `CONFIG_DRM` or any driver subsystem; fix the cause of the failure | [src: file: workflows/bootc-debs-builder/kernel/config:203-205] |
| The kernel is the kernel.org tarball of the newest stable or longterm release whose series every patch source already provides (CachyOS, ROCKNIX), resolved before each build by the `track:` entry (`kernel-org: stable`, `require-patches: kernel/patches.yml`); a release the patches have not caught up with is skipped, not built and failed with its sha256 from `sha256sums.asc`; the deb version is pinned to `<kernel>-1` so the module entries fetch the same tarball | A single home-built kernel replaces Debian's kernel source; the rolling release keeps the last-good deb when a new kernel does not build, and the checksum is verified before extraction | Don't use `apt-get source linux`, don't commit a kernel version or checksum, don't build modules against a different tarball than the image | [src: file: workflows/bootc-debs-builder/lib/kernel-source.sh:1-45] [src: file: workflows/bootc-debs-builder/packages.yml:81-113] |
| Kernel patches are never committed: `kernel/patches.yml` lists official upstream URLs (`{series}` / `{version}` placeholders), each with a stage, a license and a class (`kernel` or `module`); `kernel_apply_patches` downloads them, checks the sha256 against `patches.lock.json`, dry-runs, then applies in manifest order, and any failure stops the build | The tree stays reproducible from upstream sources, a silently changed upstream patch is caught by the guard, and a patch that no longer applies to the rolling kernel breaks loudly instead of being skipped. A patch that can be a module (tristate driver or header) is class `module` and only applied for the module build; otherwise it is class `kernel`. Mixing both classes is allowed, conflicts are not | Don't commit `.patch` files, don't skip or silently drop a patch that fails to apply, don't pin a kernel commit, and don't refresh `patches.lock.json` without reviewing the diff | [src: file: workflows/bootc-debs-builder/kernel/patches.yml:28] [src: file: workflows/bootc-debs-builder/lib/kernel-patches.sh:43] |
| Android phones are out of scope for the embedded profile; it covers arm64 boards whose firmware loads U-Boot | Phones need their own boot chain and vendor trees and live in a separate repository | Don't add phone SoC patches or device trees to `kernel/patches.yml` or the `kernel/modules/*` overlays | [src: file: Containerfile.minimal:12] |
| The minimal image keeps systemd and dbus (option A) rather than a lighter init | The login stack, `bootc`, `systemd-timesyncd` and ssh depend on them; the memory savings come from kernel machinery, not from replacing the init | Don't swap the init or drop dbus to chase the idle-RAM target without a new decision | [src: file: docs/minimal.md:103] [src: file: Containerfile.minimal:117] |
| Inference-oriented kernel options (lazy preemption, madvise-only THP, multi-gen LRU, zram, zswap off by default) are added without measurement | Only compatibility was checked | Don't claim a performance gain without a measurement |
| arm64 has two kernels, 4 KB pages (Raspberry Pi 3 and 4) and 16 KB pages (Raspberry Pi 5, RK3588), published as two images (`<tag>` on 16 KB, `<tag>-4k` on 4 KB); it is the one exception to the single-kernel rule, amd64 keeps one kernel | The page size is a compile-time choice, so it cannot be a module, and neither the Cortex-A53 nor the Cortex-A72 has a 16 KB granule (their TRMs). The owner keeps the old devices working without giving up the gains of recent hardware, and 16 KB pages are becoming the norm | Don't put `ARM64_16K_PAGES` in the shared `kernel/config` (it would stop the Pi 3 and Pi 4 from booting), don't install one kernel's modules on the other, and don't add a third page size without the same reasoning | [src: file: workflows/bootc-debs-builder/kernel/config:367] [src: file: docs/kernel-patches.md:1] |
| The `kernel/modules/arm` and `kernel/modules/x86_64` overlays are merged into the kernel build (`linux-image`, `linux-image-16k`); only the per-device packages (`linux-modules-rpi3`, `-rpi4`, `-rpi5`, `-rk3588`) remain as separate modules packages, depending on their kernel. `linux-modules-arm[-16k]`, `linux-modules-x86-64` and `linux-modules-generic` are gone | Those packages were always installed with the kernel, so the dependency was useless, and a modules-only build cannot add the built-in (`=y`) options their overlays carry (17 in `arm`, 5 in `x86_64`). Device packages keep per-device CI cache granularity | Don't re-create a base modules package under the kernel. An edit of `kernel/modules/arm` or `x86_64` now rebuilds the kernel (build time not measured), and since `sources:` is not per-arch an x86_64 overlay edit also invalidates the arm64 kernel cache |
| Module signing is a CI option: when active, the kernel build signs kernel and device modules with the one CI key, forces `MODULE_SIG_FORCE` and builds the secondary and machine (MOK) keyrings, and fails if `olddefconfig` drops one; when inactive nothing is signed and nothing is forced. The installer's `mok-stage` enrolls the Secure Boot certificate plus every public certificate found in `/usr/share/debian-bootc/mok.d/` in one `mokutil --import` | A fork keeps its own key (no key sharing, each layer is its owner's responsibility) and adds its certificate without a rebuild; one request means one MokManager password | Don't force signature checks when signing is inactive, don't distribute a private key (files holding one are refused), don't split the enrollment into several imports | [src: file: workflows/bootc-debs-builder/lib/kernel-signing.sh:1-20] [src: file: src/buildisopreinstall/usr/libexec/debian-bootc/mok-stage:1-15] |
| Signing mode `both` shares everything but the kernel: modules are always signed and live in one package set and one `debs-cache`; only the kernel package exists twice (`daemoncores-kernel-<kver>` and `-nosign`, which Provides the signed name so the modules install on either), for amd64 and the 16 KB arm64 kernel; the 4 KB arm64 kernel and the U-Boot profiles have no signed variant; `CONFIG_MODULE_SIG` is on in every kernel and only `MODULE_SIG_FORCE` follows `KERNEL_SIGNING_ENFORCE`; both variants install from the single APT suite and an image opts into a `<tag>-nosign` twin with the `org.daemoncores.unsigned-kernel-image` label | A signed module loads on a kernel that does not force signatures, so a second module set and a second cache would double storage for one signature difference; `CONFIG_MODULE_SIG` changes `struct module`, so it must match across kernels | Don't split the cache or the modules by signing mode, don't build a signed variant for U-Boot profiles, don't add a second APT suite | [src: file: workflows/bootc-debs-builder/packages.yml:78] [src: file: workflows/bootc-debs-builder/lib/kernel-signing.sh:77] |
| Automatic updates have one image per tag: the bootc timer is on by default and a symlink `/etc/systemd/system/bootc-fetch-apply-updates.timer -> /dev/null` (a bootc-installer checkbox) switches it off; there is no `lock` or `autoupdate` tag family and per-arch tags are `<tag>_<arch>` | A variant per update mode doubled every published image for a setting that is one file in `/etc` | Don't reintroduce a lock image or an `AUTOUPDATE` build argument | [src: file: Containerfile.minimal:53] |
| Every image builds on a shared `Containerfile.base`, and the kernel is installed in a `RUN` of its own after every other package | The signed image and its `-nosign` twin differ by the kernel package only; with the base and the package layers shared, the CI builds the base once, then the image, then the twin on the cached layers, and the twin costs the kernel layer and what follows it | Don't copy the base phases back into a Containerfile, don't add a `Containerfile.nosign`, don't move `ARG KERNEL_SUFFIX` above the packages (it would invalidate their cache), and never push the base or an image the run did not ask for | [src: file: Containerfile.base:1] [src: file: Containerfile:180] [src: file: Containerfile.minimal:151] |
